# Proposed account-deletion and reward contracts

All interfaces below are proposed, not implemented. No arbitrary target UUID/email accepted. Use existing origin/CORS policy, same-origin bearer-authenticated JSON, `Cache-Control:no-store`; require explicit allowed origin, reject cross-site requests, never log proof/token/password/email. CORS is not authorization. Provider configuration and R6 feasibility remain blocking gates.

## One endpoint: `/.netlify/functions/account-delete`

- `POST {action:'challenge'}`: validate current original owner/session, allocate request_id in the challenge record only (no deletion-request row/suspension until confirmed) and one active challenge generation, derive recipient from confirmed Auth email, issue candidate fresh OTP through supported Supabase signInWithOtp(existing user only), return `{requestId,challengeId,expiresAt}`. Five-minute app TTL, <=3/user/15min and five attempts. No client target email/UUID. R6 PoC must prove freshness; reauthenticate nonce is not accepted as verifyOtp email token.
- `POST {action:'confirm',requestId,challengeId,code,confirmation:'DELETE_ACCOUNT',acknowledgeForfeiture:true}`: **single verification+confirmation**, no separate opaque proof bearer/verify endpoint. Verify provider code server-side; compare returned UUID with original, original session_id remains validated, email version/purpose/request/challenge generation/TTL match. Provider-created session never replaces original browser session; do not return its tokens. Consume local verified receipt and persist PENDING intent in one SQL transaction. A crash after provider verification but before durable receipt requires new proof, not guessed success. If durable intent exists, resume without reauthentication.
- Persist `suspension_preparing` progress and install confirmed Redis Lua fence before recording accepted_at and responding 202 `{requestId,status:'PENDING',accepted:true,completed:false}`. SQL intent suspends SQL/WS earlier. Redis unavailable returns durable preparing/retry status/reference; no fully-fenced-acceptance claim yet, no rollback to active. Background tick completes fence/acceptance without user login. Lost response retries resolve by old owner/request/capability, not replaying financial work. Fully accepted duplicate returns current real state without consuming OTP again.
- `GET`: authenticated owner gets minimal status. After suspension general app APIs deny access; this endpoint alone may use identity-only signature/session verification and an owner-matched request query. After Auth is removed, use a random >=256-bit read-only status capability issued on acceptance (hash stored, short finite lifetime, no financial/profile reads); transport it only in Authorization/header, not URLs/logs. Without capability/valid owner return generic 401/404; no public UUID lookup. Capability expiration never blocks background completion; support reference can resolve incidents through authorized operators.
- Status shape `{requestId,status,accepted:boolean,completed:boolean,retryable:boolean,phase,notBefore?}` with redacted message and optional next retry time. Phases include suspension_preparing, processing_poker, waiting_storage_expiry, retrying_dependency, operator_review. Storage may exceed two hours; notBefore is cleanup eligibility, not completion ETA. Planned waits are not incidents; financial inconsistency stops destructive steps immediately. Do not expose table IDs, balances, email HMACs, old transaction/history or internal diagnostics.
- Errors: 400 malformed/confirmation missing; 401 invalid session/proof; 403 wrong subject/session or account suspended on general APIs; 409 proof email changed; 429 challenge limits; 503 dependency unavailable. Pending hand/CH balance is never a reason to reject a verified request.

Status capability proposal: 24h absolute TTL, rotation by valid owner while still present, no account authority. UI may stop polling on expiry without claiming deletion complete. Owner reviews delayed completion/status UX with architecture.

## Internal lifecycle interfaces

`withAccountLifecycleLock(tx,userIds,fn)`: transaction-scoped locks sorted/deduplicated by UUID. `assertAccountActive(tx,userId)`: authoritative Auth existence plus request/retired state; explicit denial on unavailable state. `requestAccountDeletion(tx,{oldUserId,sessionId,proofReceipt,confirmation})`: consume and upsert intent; no network/table action under lock. `advanceAccountDeletion(deps,requestId)`: fenced step progression and durable retry; only trusted WS service adapters can invoke financial/table actions.

Ordinary operations after suspension return terminal `account_deletion_pending` or `account_deleted`; clients stop retries and clear account/award session. Valid anonymous gameplay remains unchanged; presenting old UUID as an anonymous source does not bypass suspension. Internal settlement permission comes from server code and persisted obligation, never request JSON, JWT metadata or client-selected purpose.

Keep current welcome/bonus response shapes and existing UUID idempotency keys. Add reasons `welcome_bonus_limit_reached`, `already_claimed_by_identity`, `verified_email_required`, `reward_identity_unavailable` with eligible=false. No extra CH source or signup rejection.

## Internal Redis write contract (T005/T007/T013/T014)

Existing store helper accepts only trusted target UUID/current epoch and bounded server-built mutations, not a public arbitrary-key/command interface. ACTIVE+matching epoch check and all creating/renewing writes execute in one Redis Lua call; no client-side check then raw SETEX/ZADD. Session touch checks stored owner and existing session in that call. Snapshot/status-only/boost/admin backfill/visibility-sync use this same contract, with explicit denial propagation. Specialized award/migration/visibility scripts retain their logic and add matching checks. Removal-only persisted cleanup/prune is exact-owner, replay-safe and cannot restore data, clear fence/epoch or delete shared sets. No cross-store atomicity is asserted. Refer to research.md inventory for every caller; feature activation requires old raw writers drained.

## Closure and recovery contract

Only finalizer may close/retire USER or hard-delete Auth. Completed means financial seal/receipt, required private cleanup, capability horizon and verified Auth removal all done. Retry unknown outcome by original idempotency/progress evidence. No API returns completed for a durable intent alone. Incident does not re-enable account; operator tooling must use current access controls and preserve audit evidence.

## Proof security and rollout prerequisites

Common OTP is a candidate, not a proven request-scoped credential. Public reauthenticate API sends a nonce documented for password update; verifyOtp public types do not expose reauthentication nonce verification. Existing OTP may be login-purpose and create a new session. Merely storing request_id locally cannot prove provider code freshness. R6 separate-GO PoC in research.md/quickstart must establish old-code invalidation, concurrent flow isolation, exact original session/UUID binding and Google-only compatibility. Otherwise stop and redesign before implementation.

Legacy signed-upload rollout gates in research.md are mandatory before enabling deletion: no old signing/cleanup invocation remains, two-hour capability lifetime plus validated in-flight/clock bound passes, surviving rows backfilled conservatively and scoped unknown-path orphan cleanup confirmed. New rows persist until capability-safe final cleanup; no COMPLETED for a live/recreatable path. Account-status capability expiry never requires user to log in to continue deletion.

Private WS delivery must authorize and enqueue/send under the same lifecycle serialization as acceptance (no unlocked await gap after ACTIVE check); socket close alone is insufficient. Redis writes require ACTIVE permit and matching recovery epoch atomically in Lua (missing denies, NX initialization cannot override BLOCKED); a network timeout does not prove cancellation. No Postgres+Redis atomicity claim.
