New lifecycle/closed checks must run for all new USER entries, including admin grants, transfers and arbitrary recipients; an API-only guard is insufficient. Internal settled cash-out is allowed only against persisted obligations before the financial seal. New postings after seal fail closed; existing idempotent internal replay may return original evidence without creating an account or money.

Retention breaking change: `supabase/migrations/20260904170000_chips_ledger_closed_human_prune_whitelist.sql` and Production `20260914090000_chips_ledger_production_retention_contract.sql` require matching live `accounts.user_id` and `bool_and(status='active')`. Also audit `fetchCurrentUserAccountSnapshot()`, snapshot export, archive replay and all USER identity joins in retention helpers. Do not rewrite historical payload/hash/UUID metadata to make proofs pass. If compatibility proof fails, retirement release is blocked; do not silently disable safe retention forever.

Before acknowledging acceptance, install and confirm the Redis marker, then commit accepted_at under lifecycle lock. Persist request intent first with suspension_preparing progress so a crash between systems is resumable and DB paths are already denied; after intent the user cannot cancel/resume play. If Redis is unavailable return truthful preparing/retrying status with durable request reference, not completed or fully fenced acceptance. Recovery installs barrier and records accepted_at without login. Any delayed Redis command executes either before the marker (included in cleanup) or after it (denied by Lua); do not claim Postgres+Redis atomicity. Never automatically clear an uncertain Redis fence to compensate a lost SQL response; reconcile persisted intent under user lock. Redis restart/flush must disable authenticated XP writes until barriers reload from authoritative pending/retired identity, with lifecycle checks preventing guest-source bypass. Marker retention covers all possible old-session/queued-write lifetimes and cleanup; Auth nonexistence/retired UUID checks prevent indefinite guest resurrection afterward. Private WS dispatch must recheck lifecycle at delivery, with no positive ACTIVE cache that can outlive acceptance. Already transmitted network bytes cannot be recalled; guarantee covers operations/deliveries authorized after the barrier.

## R3 — durable recovery, no extra daemon

Decision: extend existing WS `sweepOpenTableJanitorAndBroadcast()` tick (default 60 s) with a separate bounded deletion-request scan, also at startup and after successful settlement. Scan requests even when zero open tables exist. Reuse existing process supervision, DB and table queue. New focused shared `shared/account-deletion.mjs` carries request/finalization steps consumed by Netlify and WS; only WS drives gameplay progression. No new worker service, scheduler or cron. If existing service is down, requests remain durable and suspended until restart; operator-visible backlog is mandatory.

**Revised recovery bounds:** keep the owner's accepted existing WS tick (default 60s), separate due-request cursor including no-table and Auth-retry requests, startup scan and post-settlement wakeup. Ten requests is a maximum fetched batch for modest load, not ten complete workflows per tick or a throughput guarantee. Process bounded steps with round-robin due scheduling and no overlapping sweep; each request yields after one externally blocking step; acquire its lease only when starting it, never lease all ten up front. Per-tick elapsed-work budget is 15s: yield between steps and reschedule remaining due requests to next existing tick, with a single external step deadline <=15s (not a hard tick wall-clock SLA). Benchmark/backlog tests can lower batch size; no configuration/service additions justified now.

Keep 120s DB lease only as a safety margin over one bounded step (proposed external deadline <=15s, DB step timeout <=5s); no heartbeat framework and no long hand/upload under lease. Lease is per step; waits release it and persist next_attempt_at. Timeout cancellation is not proof an external request stopped. Lease generation/CAS prevents stale progress writes; external financial/cash-out keys are already idempotent, Storage delete uses exact manifested path and Auth delete exact old UUID. Reconcile uncertain outcome before another destructive step. Scope every predicate/path to request owner; never wildcard-delete someone else's data.

Simplify alerts: remove independent 10-errors threshold. Open one deduplicated operator incident after **30 minutes overdue for actionable progress**, or immediately on inconsistent financial evidence; count attempts only for diagnostics. Timed Storage waits, an ordinary ongoing hand and scheduled backoff before due time do not advance the overdue timer. Store wait reason, due_at and last durable progress; surface waiting status rather than error. During Supabase outage fail closed, emit one redacted klog service incident when durable writes are unavailable, and retry from persisted last step after reconnection; record incident state when DB returns. Retry once per existing tick with exponential backoff 60s–5min, no retry limit that discards an accepted request. VPS restart loses no intent; no-table accounts resume without login/browser action. Financial ambiguity freezes burn/retirement/Auth removal and requires explicit operator reconciliation, not automatic retry into a guessed result.


Final predicate: no live/runtime or persisted seat/hand liability, no pending JOIN/rebuy/cash-out or late-grant path, matching final settlement evidence, zero unresolved per-user obligation (not global table escrow zero), final BURN committed once and USER closed; private Redis/profile/Storage cleanup confirmed, signed upload horizon passed, then hard Auth delete. Zero balance produces a durable no-burn receipt, never a zero-value ledger entry. Lost Auth response is reconciled by old UUID lookup; not-found is success only after prior finalization evidence. Never infer success from timeout or unrelated API 404.

## R5 — purpose-bound retention recommendation (owner review 2026-10-17)

**Accepted business rule:** maximum three successful welcome payouts per recognized verified email, without timeout. Daily remains once per identity/UTC day and once campaigns once per identity/campaign. HMAC technique accepted; a rolling 12-month reset is rejected and removed from the design. Technical recommendation below is not a finding that Article 6(1)(f) authorizes this processing.

**Technical minimization:** retain only domain-separated versioned HMAC, saturated welcome paid count 0..3 (imported >3 represented as exhausted), minimal dedupe evidence for successful source payments, and last successful update/retention-purpose reference. At most three welcome payment proofs are needed for eligibility; do not build a full account history. No email, profile, IP/device identifier, login timestamps or unsuccessful attempt history in the reward registry. Source receipts exist only to make import/ledger retry exactly-once and remain private; remove unnecessary per-award detail after its reconciliation purpose ends without resetting the saturated count. Transactional count/proof and payment remain indivisible. A separate payment audit follows its existing policy and cannot silently become a second anti-farming registry.

**Purpose-bound retention schedule proposed for privacy approval:**

| Proof | Retain while | End of purpose / review |
|---|---|---|
| Welcome HMAC + saturated count | Same welcome program continues to offer the benefit whose three-payout cap must survive deletion/recreation; no age-based expiry | Annual documented necessity/proportionality review; permanently close program and remove ability to restart it with reset counters before erasing. Short campaign pauses, renamed config and new UUIDs are not program termination. Purge within 30 days after genuinely final closure, subject only to separately established legal-claim/audit obligations. |
| Poker Daily identity/day receipt | UTC day plus 48h reconciliation margin; operations use server decision day and cannot backdate claims | Purge after this margin once uncertain postings reconciled; old-day retry must return existing financial result without paying or opening yesterday's eligibility. Unresolved receipt kept only for documented incident purpose, not blanket extension of all proofs. |
| Once identity/campaign marker | Campaign may still be claimed, resumed or retried | Ended/archived campaign must be irreversibly non-claimable/non-reopenable before removing markers; purge within 30 days after final closure and resolution of uncertain payments. If reactivation remains possible, the original marker must survive. Changing title/code never creates new eligibility. |

The 30-day purge SLA bounds disposal after purpose ends; it does not reset welcome while the program runs. An annual review is a controller operation in existing governance, not a new runtime cron. If continued necessity cannot be justified, disable that reward program/campaign and resolve retention/rights before removing proof; do not silently change the three-payout promise. Program-lifetime retention may be long and end-date unknown, but is tied to a specific continuing abuse risk, documented review and enforceable termination/purge, not an unrestricted perpetual tracking license. Owner/privacy review must assess actual abuse likelihood, CH economic impact, less intrusive alternatives (UUID-only and short rolling windows fail delete/recreate protection), user expectations and safeguards. No automatic assumption that all future programs can reuse this registry.

**Legal assessment still required:** assess Article 6(1)(f) through documented purpose, necessity and balancing (LIA), with transparency under Article 13 including retention criteria, strict access and purpose limitation under Article 5. Pseudonymous HMAC remains personal data. Article 17 erasure and Article 21 objection are not categorically excluded by an anti-abuse label; assess the individual request and compelling grounds, and restriction under Article 18 where applicable. Do not assert that 6(1)(f) is itself an Article 17(3) exemption. If erasure/objection must be honored, remove the relevant proof under the approved rights workflow and document inability to recognize that identity thereafter; the business rule stays unchanged, but historical enforcement cannot be guaranteed for legally erased evidence. No covert denial of signup/deletion or indefinite rights-blocking hold. Legal/privacy reviewer must approve this exception handling and user notice; controller identity and responsible owner must be assigned before release.

**Canonicalization:** trim whitespace, lowercase consistently with actual Auth semantics and normalize domain; confirm case/Unicode behavior before HMAC v1. Do not strip plus-tags/dots or infer the same physical person from aliases. Trust authoritative confirmed email, never editable user_metadata. V1 cannot prevent different verified addresses. Existing known verified accounts can be imported from confirmed successful payouts; previously deleted identities without trustworthy email cannot be reconstructed. State enforcement start/coverage honestly; do not mint compensation or claim an all-history guarantee.

**Key lifecycle:** prefer stable keyed identity derivation for the program, rotate secret-encryption/wrapping/access credentials independently. If HMAC digest key itself changes, evaluate all supported versions under deterministic locks and link to one private identity on next verified encounter; preserve prior recognition keys for every still-needed deleted-identity marker. Without raw email it is impossible to recompute every historical digest under a new key offline. Therefore do not promise to retire an old derivation key after an arbitrary overlap: unencountered deleted identities would receive fresh counters. Bound supported versions operationally; actual key compromise/loss or rotation requiring destruction of a recognition key is an incident and design/legal decision before protected payouts resume.
