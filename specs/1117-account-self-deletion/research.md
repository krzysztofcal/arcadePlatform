### A — immediate central denial: distinguish the actual authority

[Supabase Storage access control](https://supabase.com/docs/guides/storage/security/access-control) explicitly states service keys bypass RLS. Provider signed upload path verifies the path-bound capability and then performs superuser upload; it does not re-check Arcade lifecycle. Removing an object/intent does not revoke its token. These proposed A variants FAIL the criterion by documented architecture, not because a test was blocked.

SQL triggers are different from RLS: the existing public.account_upload_intent_v2 BEFORE INSERT calls account_guard_owned_write_v2 and rejects non-ACTIVE UUIDs under the lifecycle advisory lock even for ordinary service_role DML. All identified helper families insert an intent before calling Storage signing. The trigger does NOT cover direct provider signing, an existing signed token, or an in-flight output write. [Supabase advises treating its managed Storage schema as read-only](https://supabase.com/docs/guides/storage/schema/design); a new storage trigger would need provider support, ownership design, atomic race proof and upgrade validation. It is not an existing proven minimal primitive and is NOT recommended for V1. Bucket size/MIME limits are upload validation, not an identity/capability revoke fence. A shared credential/signature-trust revocation can centrally remove authority, but must revoke the authority actually used. [API-key documentation](https://supabase.com/docs/guides/getting-started/api-keys) says adding new keys does NOT revoke legacy keys. [JWT signing-key documentation](https://supabase.com/docs/guides/auth/signing-keys) distinguishes API keys, legacy JWT service_role and Storage signatures; removing the old Netlify environment value or changing Auth signing keys alone does not prove all Storage tokens are rejected. No supported per-upload-token revocation was established. Even effective key revocation is not a cancellation proof for uploads already admitted.
