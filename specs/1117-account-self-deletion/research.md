## R1 — ledger, escrow and retirement

Decision: retain original financial account ID, type USER, entries, transactions, sequence numbers, payload hashes, replay JSON, registry and archive receipts. On finalization burn wallet through `netlify/functions/_shared/chips-ledger.mjs::postTransaction({tx,txType:'BURN',...})` using `shared/poker-domain/gift-purchase.mjs::executePokerGiftPurchase()` USER(-)/GENESIS(+) pattern. Do not expose generic BURN in `chips-tx.mjs`. Wait for all table obligations; burn once after final seal, not independently on each intermediate cash-out.

Catalog blockers: `chips_accounts_user_id_fkey` is NO ACTION; both `chips_accounts_user_or_system_key` and `chips_accounts_user_system_exclusive` require USER.user_id non-null. `chips_entries.account_id` references account; deleting account loses or blocks financial history. Proposed `retired_user_id` preserves original UUID without Auth FK, while live `user_id` becomes NULL only for closed, zero USER with retirement timestamp. Update both CHECKs, retain live uniqueness and add retired identity uniqueness. Do not change USER to SYSTEM or invent a synthetic Auth user.

`postTransaction()` currently checks SYSTEM status but not USER status. `getOrCreateUserAccount()` could recreate an old wallet after detachment. New lifecycle/closed checks must run for all new USER entries, including admin grants, transfers and arbitrary recipients; an API-only guard is insufficient. Internal settled cash-out is allowed only against persisted obligations before the financial seal. New postings after seal fail closed; existing idempotent internal replay may return original evidence without creating an account or money.

Retention breaking change: `supabase/migrations/20260904170000_chips_ledger_closed_human_prune_whitelist.sql` and Production `20260914090000_chips_ledger_production_retention_contract.sql` require matching live `accounts.user_id` and `bool_and(status='active')`. Narrowly recognize `(live user_id OR retired_user_id)` and closed-zero retired USER for financial identity/proof; keep human classification and table fence intact. Also audit `fetchCurrentUserAccountSnapshot()`, snapshot export, archive replay and all USER identity joins in retention helpers. Do not rewrite historical payload/hash/UUID metadata to make proofs pass. If compatibility proof fails, retirement release is blocked; do not silently disable safe retention forever.

## Poker: forced Leave and all-in

Reuse `shared/poker-domain/leave.mjs::executePokerLeave()`, `postHumanLeaveCashoutInTx()`, `finalizeDeferredLeavesAfterSettlement()`, WS `handlers/leave.mjs::handleLeaveCommand()`, `persistence/authoritative-leave-adapter.mjs::createAuthoritativeLeaveExecutor()` and `deferred-leave-finalization-adapter.mjs`. Domain Leave locks table/state/seat, persists ledger in caller tx, and defers live-hand detach. Always enqueue through existing table command queue; Netlify may persist intent but must not directly mutate live Poker state.

Critical finding: both `netlify/functions/_shared/poker-reducer.mjs::applyLeaveTable()` and `ws-server/poker/snapshot-runtime/poker-reducer.mjs` mark participating all-in players folded, delete stacks and mark left. Showdown and required-hole-card selection exclude these identities. Skipping only `folded=true` is insufficient. For deletion all-in, persist pending detach separately from the gameplay left flag, preserve hand seats/stack/contribution/hole cards and showdown eligibility, deny further user commands, and invoke normal Leave/cash-out only after settled. Use existing deferred seat state where its predicates permit; add only the smallest pending-delete marker necessary, not a second poker engine. Non-all-in uses current fold semantics. Regression tests must cover all-in winner/loser, split side-pot and last human versus bots in both reducer paths.

Enumerate seats plus authoritative runtime and persisted unresolved hand participation: no-seat alone is not proof of no liability. For each table restore through existing bootstrap when absent, serialize Leave/settlement, retain receipts and retry unknown outcomes. Do not clear private snapshots until obligations are conclusively settled. Existing `runSettledRolloverCommand()` retries deferred finalization; notify account progression after it succeeds.

## R2 — access and write-path inventory

- Shared HTTP `netlify/functions/_shared/supabase-admin.mjs::verifySupabaseJwt()` local signature validation; separate `ws-mint-token.mjs::verifySupabaseJwt()/handler()`; `_shared/admin-auth.mjs` and service-role jobs bypass ordinary client RLS. Check live Auth existence/session and deletion state, with explicit terminal denial, then enforce inside mutations too.
- Endpoints: `chips-balance.mjs`, `chips-ledger.mjs`, `chips-tx.mjs`, welcome/bonus APIs; `poker-create-table.mjs`, `poker-quick-seat.mjs`, `poker-progression.mjs`, `poker-export-log.mjs`; profile-me/avatar endpoints, favorites, xp and leaderboard APIs, start-session/calculate-xp; privileged grant/admin routes. Audit all verifier callers and all posting recipients, not just listed URLs.
- WS `poker/auth/verify-token.mjs`, `handlers/auth.mjs`, `runtime/session.mjs`, `runtime/session-store.mjs`, `server.mjs::processMessage()` currently retain authenticated identity. Check before auth, protected commands, snapshots/private broadcasts/reconnect and automatic user rebuy/re-entry. Reuse `connectionsForUser()` and existing `invalidateSocketSession()`; close and unsubscribe connections once marker observed. A push/close is a latency optimization, never the financial authorization source.
- Catalog: favorites SELECT/INSERT/DELETE, chips own-account/entries SELECT, poker seats/actions/requests/tables SELECT use `auth.uid()`/seat ownership without lifecycle. Add active-account predicate to client policies and invoker views. Bonus/profile tables deny public already; preserve that. New private tables/functions revoke PUBLIC/anon/authenticated access; RLS alone does not constrain service-role SQL. Audit realtime subscriptions so private emission checks the same fence.
- XP: `start-session.mjs` and `calculate-xp.mjs` already reject an explicitly supplied invalid JWT; preserve that behavior. No-JWT caller-controlled anonId/userId can be an old UUID. `xp-identity` migration source must also reject suspended/retired UUID; do not let old UUID reappear as guest and merge XP into the new account.

Decision: one lifecycle helper and stable per-user PostgreSQL advisory transaction lock used by acceptance and every affected mutation (including admin target). Multi-user transfers acquire user locks in sorted UUID order. Poker table transaction lock comes before lifecycle user locks; bonus campaign lock precedes identity lock, then sorted user locks, then ledger account locks. Acceptance holds only user lock and durable intent, never waits for a table under that lock. Recheck ACTIVE after acquiring it. Finalizer handles tables first, releases table locks, then takes user lock and proves obligations sealed. No path may take table/campaign/identity lock after holding user lock. Deadlock/serialization retry restarts entire transaction with stable idempotency key.

For Redis operations hold the same lifecycle lock across bounded Redis mutation/profile persistence; acceptance cannot commit before already-authorized writes finish. Timeout/uncertain Redis result stays pending for cleanup. Add Lua deletion barrier as defense in depth, but do not claim a Postgres+Redis distributed atomic transaction. Private WS dispatch must recheck lifecycle at delivery, with no positive ACTIVE cache that can outlive acceptance. Already transmitted network bytes cannot be recalled; guarantee covers operations/deliveries authorized after the barrier.

## R3 — durable recovery, no extra daemon

Decision: extend existing WS `sweepOpenTableJanitorAndBroadcast()` tick (default 60 s) with a separate bounded deletion-request scan, also at startup and after successful settlement. Scan requests even when zero open tables exist. Reuse existing process supervision, DB and table queue. New focused shared `shared/account-deletion.mjs` carries request/finalization steps consumed by Netlify and WS; only WS drives gameplay progression. No new worker service, scheduler or cron. If existing service is down, requests remain durable and suspended until restart; operator-visible backlog is mandatory.

Proposed defaults: scan <=10 requests/tick, no overlapping sweep, short DB claim lease 120 s with owner/fencing generation and heartbeat for bounded steps. Persist step intent/result before/after external actions; release DB locks for network calls. `next_attempt_at`, capped exponential retries 5 s–5 min, incident after 10 consecutive failures or no progress 30 min. Incident stays suspended, automatic reconciliation may continue safe steps; ambiguous financial steps require operator resolution. Round-robin by due time prevents one stuck table starving others. Lease expiration alone never authorizes destructive work if an earlier external operation could still complete; steps have durable receipts and finalizer rechecks fencing token before committing.

Final predicate: no live/runtime or persisted seat/hand liability, no pending JOIN/rebuy/cash-out or late-grant path, matching final settlement evidence, zero unresolved per-user obligation (not global table escrow zero), final BURN committed once and USER closed; private Redis/profile/Storage cleanup confirmed, signed upload horizon passed, then hard Auth delete. Zero balance produces a durable no-burn receipt, never a zero-value ledger entry. Lost Auth response is reconciled by old UUID lookup; not-found is success only after prior finalization evidence. Never infer success from timeout or unrelated API 404.

## R4 / R8 — one private reward-proof mechanism

Decision: one private identity row plus minimal paid receipts for welcome, Poker Daily and once campaigns. HMAC from authoritative confirmed email, resolve/lock identities in consistent version order, recheck ACTIVE, campaign eligibility and canonical UTC clock inside the transaction; call existing `postTransaction({tx})`, insert proof, and commit together. Welcome count derives from retained paid receipts (max three, no need for independent unsynchronized counter). Lock identity even when no receipt exists; unique constraints are the final backstop. Replay verifies original receipt/ledger and returns it without new proof or count. Historical registry lookup is necessary when live transaction was archived; unknown payout outcome fails closed until reconciled.

`welcome-bonus.mjs::getWelcomeBonusStatus()/claimWelcomeBonus()` currently preflights then posts outside a caller transaction. Extend it to `beginSql`, with stable existing UUID payout idempotency key. `bonus-campaigns.mjs::claimBonusCampaign()` already locks campaign, uses `transactionClock`, rechecks midnight and commits ledger+bonus_claims atomically; extend that transaction. Preserve `buildCampaignIdempotencyKey()` for old replay; identity uniqueness is additional, not a destructive key replacement. GET status is advisory and must display identity denial; POST rechecks. Scope Poker Daily uniqueness to reward family `poker_daily` + UTC date, not campaign UUID, so creating a second Daily campaign cannot pay twice. Once promotions use immutable campaign UUID, not editable title/code; recreating a campaign is a new promotion and requires explicit admin intent. Preserve unrelated daily/weekly/monthly behavior and all maxTotalClaims limits.

Additional finding: `bonus_claims.user_id ON DELETE CASCADE` can lower `max_total_claims` counting after deletion. Count retained paid financial campaign evidence rather than surviving user claim rows, without double-counting the new identity proof and original claim. Allowlist rows cascade intentionally (no inherited eligibility). `bonus_campaigns.created_by` and `bonus_campaign_eligible_users.created_by` NO ACTION FKs must be made nullable SET NULL or explicitly scrubbed without deleting campaigns/other recipients. Do not delete another user's eligibility because the deleted user was its administrator.

Legacy coverage: before enabling deletion and identity enforcement together, backfill known successful welcome/Daily/once payouts of existing verified accounts in bounded server transactions, without minting CH. Store private source receipt uniqueness so first claim cannot count imported payout twice. Same identity across extant UUIDs aggregates payments (saturate eligibility at >=3, never refund or claw back). Include confirmed ledger/registry evidence, not signups. Deleted historical identities without trusted verified email cannot be reconstructed; document horizon/start and limitation. Backfill must precede deleting its Auth lookup source. A concurrent email change invalidates challenge and forces authoritative email reread under the same Auth-row/lifecycle serialization before grant; V1 cannot prevent deliberate rotation to genuinely different verified addresses.

## R5 — proposed privacy policy, not a legal conclusion

Proposed decision for review: rolling 12-month per-payment welcome/once receipts; Daily proof until UTC day-end plus 48 h retry margin. A failed signup/claim must not extend expiry. No evergreen `last_seen` refresh, no resetting expiry of old payouts when a new payout occurs. Welcome count is number of unexpired payments, not a permanent lifetime cap; a long-running once campaign can be farmed after evidence expires unless campaign end is within the retained horizon or a separately justified longer window is approved. This incompatibility is a release decision, not something to hide in implementation. Unknown historical coverage cannot truthfully be called all-time.

Canonicalization proposal: trim surrounding whitespace, lowercase according to existing Auth email semantics, normalize domain consistently; never strip plus-tags/dots, merge provider-specific aliases or rely on Google `sub` for V1. Confirm case/Unicode handling against actual Auth behavior before freezing HMAC v1. Reject missing/unverified email for protected reward claim only. Keep no raw email in proof/request/logs. HMAC domain separation/version: `reward-email:v1`, secret stored only in existing server secret facilities, separate from JWT signing key. No secrets configured in this audit.

Rotation: read active+previous HMAC keys for the whole unexpired horizon, lock candidates in deterministic order and consolidate under one private identity; never count them as separate people. Keep previous key until its final proof expires; loss of a key or missing overlap fails protected claims closed and raises incident instead of silently resetting counts. Do not rotate by copying only active logged-in users, which misses deleted identities.

Erasure: proof is pseudonymous personal data; retention on deletion requires reviewed purpose/lawful basis, disclosed period and legitimate erasure-request handling. Where retention cannot be justified, erase proof and accept/document reduced anti-abuse coverage; do not deny deletion to retain a bonus counter. Existing ledger UUIDs/metadata/replay/archive financial audit have separate approved retention; do not mutate immutable payload hashes to remove them. Inventory names/free text in historical metadata separately, minimize future payloads, and restrict access. Existing browser/CDN copies and backups expire under their actual policy; origin deletion cannot promise to recall downloaded public avatars.

## R6 — recent proof options

Preferred: one server-mediated verified-email OTP challenge for both password and Google-only accounts. Bind random challenge to authenticated old UUID, original session, purpose, authoritative confirmed email version, five-minute TTL and single use; no submitted email target. Supabase send/verify endpoints must use existing user only (`shouldCreateUser:false`), returned verified Auth UUID must match, rate-limit issuance/attempts. Consume proof and persist PENDING in the same acceptance transaction; do not expose new auth credentials in logs or persist passwords/OTP in DB. Confirm that code verification is for the newly issued challenge and not an unrelated existing auth flow. Missing verified email needs genuine provider reauth feasibility rather than silently weakening deletion protection; support/manual rights path remains.

Alternative: server password token grant and returned-sub equality for password accounts; Google-only still needs provable fresh challenge. Ordinary `signInWithGoogle()`/`prompt=select_account` may silently use an existing provider session; JWT refresh `iat` is no proof. Do not select a nonce API meant only for password-change reauthentication without proving it authorizes this purpose. R6 remains unresolved until exact API behavior/config and approved disposable-account proof establish this contract. If OTP unavailable, return to design review before feature code; no new mail framework or OAuth framework authorized.
