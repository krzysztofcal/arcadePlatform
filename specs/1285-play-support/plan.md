## Design boundaries and simplified execution
Use existing Stage and Production Supabase, Netlify, WS, Android package IDs, current CI and release procedures. Official Java Play Billing (proposed 9.1.0; verify supported release and compile), existing Capacitor 8.5.3/generated Android build. No RevenueCat/SaaS, extra Netlify site, VPS, third app environment, generic cosmetics engine, general clock sync, WS bus, persistent Stage daemon, DB-wide semaphore or new admin UI. Single entitlement authority, single token processor/retry inbox, existing UI/profile/cache paths. Four delivery stages (foundation; native; presentation; release), small independently reviewed Draft PRs. Test critical logic only. Native/Stage mock proof can precede finished cosmetics; full license acceptance and release need all applicable features. See task dependencies, not numerical task order.

## A. Payment Foundation — T007/T008, critical T018 tests

### A1. State and persistence
Add forward-only private.play_support_bindings, play_support_intents, play_support_receipts, play_support_entitlements, play_support_preferences, one bounded durable work inbox and one reconcile cursor. Use sole entitlement relation unique active user+SKU, unique source receipt; provider receipt facts separate from grant/ack and public preference. No mutable ownership mirror. Dedup package/token SHA-256, prevent cross-package reuse, immutable binding/SKU, minimal restricted order ID; encrypted raw token while required. Work rows indexed by due/lease/generation, bounded dedup event metadata not raw event history; terminal evidence monotonic. Nullable owner/binding links after deletion; never cascade financial evidence from auth.users. Stable opaque random <=64-char account binding per active UUID/env via setObfuscatedAccountId (not email, Google ID, raw UUID, or random per-attempt identifier). No raw token exposed in JS/WebView, client URLs, logs, Crashlytics, public projection, or SQL/HTTP errors; provider URL token redacted.

Checkout, provider and fulfillment are separate:
- PREPARED: slot per binding+SKU, expire/cancel only if permit never consumed. Native durable private attempt ID/proof (hash server-side), NOT_INVOKED before authorize. Server atomically associates same attempt and moves LAUNCH_UNRESOLVED before SDK launch; authorize/recover idempotent for same authenticated original active account/intent/attempt/proof, recheck gates, can replace expired same-attempt capability, not a new slot.
- LAUNCH_UNRESOLVED: serialize authorize/recover/cancel/launch and callback generation. Persist INVOCATION_STARTED synchronously before BillingClient call; invoke once per attempt. Lost response or restart before marker -> recover same permit or cancel with same-attempt no-invocation evidence, not stranded. Crash after marker before/after SDK call is ambiguous; no second prompt based only on app close, disconnect, TTL, empty restore or lost native record. Definitive same-attempt nonlaunch/cancel evidence with no known token/pending/receipt may close; no blind force-buy. Late server response after cancellation/switch rejected. Escalate unresolved at 24h; preserve verified late purchase regardless of slot closure.
- PLAY_PENDING: provider verified PENDING token, block same SKU; no grant/ack, no checkout TTL applied. On PURCHASED or CANCELLED/void transition based on authoritative Google state. RECEIPT_LINKED: durable verified receipt processed; active ownership or unresolved paid support blocks re-buy. CLOSED: no-launch evidence or authoritative terminal outcome; retain justified attribution/anti-replay evidence.
- Receipt fields independent: provider UNKNOWN/PENDING/PURCHASED/CANCELLED and confirmed VOID/REVOKED; fulfillment NOT_GRANTED/GRANTED/REMOVED/UNGRANTABLE; acknowledgement NOT_ELIGIBLE/DUE/IN_FLIGHT/CONFIRMED/UNCERTAIN, attempt ID and timestamps, support status. Transient errors never provider terminal. Stable verified binding may grant original active UUID even if exact attempt/permit expired; never assign to current different account. Missing/mismatch binding, unsupported purchase, or second paid token for already-owned SKU -> restricted incident/refund path, no second grant or false ack. Ambiguous attribution = static success only. Repurchase after verified revocation requires new token/intent; old token never revived.

- Deletion before grant -> no grant/ack, paid ungrantable incident. After grant and confirmed ack -> remove normal ownership/preference/public link, preserve lawful evidence, no automatic refund simply for voluntary deletion. After grant before ack start -> disable eligibility and support/refund unresolved paid order. Refund without revocation keeps otherwise valid ownership; confirmed revoke removes only entitlement sourced from that receipt, atomic fallback if visible; later repurchase unaffected. Terminal never resurrected by old callback. Unknown/conflicting -> bounded reverify/escalate. OWNER manual Play Console refund/revoke for verified ungrantable/duplicate/unexpected real purchase, no broad money-moving authority.

### A3. Recovery ownership and budget
RTDN authenticated Google Cloud Pub/Sub push: OIDC signature/issuer/audience/expiry, verified expected push service identity, subscription/package and bounded payload; persist dedup inbox before success, test ping/permanent malformed handled safely. **HTTP 2xx is NOT Play acknowledgement.** 2xx only after durable verified grant+ack, authoritative terminal resolution, confirmed PENDING persisted with proven recovery owner, or verified ungrantable order with explicit human refund ownership. Unfinished PURCHASED, transient/ambiguous, active lease/future due without alternative proven owner -> retryable non-2xx, same-message redelivery can process due row. Preserve non2xx if persistence fails. No 2xx solely on durable commit. Future RTDN signal prioritizes current provider verification, never resurrect terminal; client immediate verify/reconnect/foreground/restore additional path, not sole recovery.
- Healthy target <=5s proposed, not SLA. Normal backoff base 30s then 1/2/4/8m, cap 15m+jitter; respect Retry-After, actual scheduler/RTDN resolution and subscription-wide best-effort push backoff. No repeated charge, no overlapping same token. Production published Netlify scheduler every 5m owns known PENDING token rechecks (~5m due even if RTDN missed, reserve due pending slot when possible), unfinished ack/grant and missed refund signals; proven actual published trigger before sale, stays ON with sales OFF. Preview cannot auto-run schedules. PENDING can exceed 24h, do not expire. Provider purchaseCompletionTime determines ack deadline (3 days from PURCHASED; unknown -> conservatively urgent), not intent time. Proposed alerts 1h unresolved, 24h manual investigation while continuing valid retries, <=24h remaining urgent/<=6h critical, pending overdue >15m/backlog. After deadline reverify actual state, no inferred refund/drop. Alert and pause new sales on material recovery outage. Terminate only authoritative terminal/verified ungrantable human-owned incident, not transient/time alone.
- Stage test deadline ~3 minutes; C1/D1 short due 5–15s / pending ~10s, Pub/Sub min/max proposed 10/30s if supported; never rely on 5m schedule. Finite supervised recovery runner (B2/T020A below) owns PENDING when ready, retains non2xx for unfinished/unknown. Actual timing measured, not guaranteed. Stage alerts at 60s unresolved or <=120s left, critical <=60s.
- Bounded per-request one token/claim, 2–3 provider calls max with timeouts ~5s, target request budget <=15s and actual push/function limit; no sleep under lock, no per-token overlap. Existing rate limits, per-token lease/fence; no global semaphore until measurement justifies. Worker <=10 candidates/5m, stop new starts by 20s, hard 25s below 30s schedule limit, requeue unprocessed; prioritize deadlines and prevent pending starvation. Daily bounded overlapping Voided Purchases cursor, one bounded page/run, checkpoint complete window only; warn lag >24h/critical >7d; >=30d gap incident, do not advance blindly, OWNER-approved bounded per-order/Console evidence recovery, no blanket revoke/regrant or full-history scan. Monitor age/backlog/drain, retries, actual calls/bytes. Illustrative full 10*288 rows/day at 1KiB ~2.95 MB/day before writes/HTTP, not measured billing; verify actual egress. Subscription retention and failure handling verified; no dropping paid work without durable transfer.
