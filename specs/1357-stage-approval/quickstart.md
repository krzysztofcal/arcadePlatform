# Operational acceptance

1. On reviewed main, inspect the environment policies and the App capability. OWNER sets up `stage-db-apply`, exactly one reviewer, main-only, admin bypass off, and approved Stage secrets after protection. Keep existing Stage automation config.
2. Request an OWNER-authorized dry acceptance from the App using the relevant trusted-main workflow with `migrations: []`, the exact current history fingerprint and an approved open PR head whose complete migration catalog matches Stage. This test bundle cannot authorize any pending SQL. Before approval check that the apply step did not start. Reject one dry run and verify no database step. After approval of a fresh dry run confirm the actual OWNER record, applied count zero and independently unchanged Stage history. If no safe no-op bundle qualifies, stop and prove the approval flow without database secrets before requesting a separate proof.
3. For real changes, compare request PR, SHA/hash manifest, history and confirmation before approving. Read back atomic receipts. A failed or uncertain result requires independent inspect and a fresh dispatch with a fresh approval if appropriate. A rerun is refused at job eligibility. Use the workflow summary to distinguish preflight refusal, rejection, missing approval and runner failure.

A pending review may hold the existing `db-stage` workflow queue. Before requesting another Stage operation, reject or cancel any obsolete pending request in GitHub. Job execution timeouts do not substitute for resolving a pending review. Preserve serialization and never bypass the queue.
