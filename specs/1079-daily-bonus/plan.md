# Implementation Plan: Poker Daily Bonus (#1079)

**Date**: 2026-10-11 | **Spec**: [spec.md](spec.md)
**Status**: proposed, awaiting review; no implementation or operational action authorized.
**Inspected source**: current `origin/main` at `1ba99776ff427783f858e075d3474e144c3947b3`, not the unrelated local gift-shop branch.

## Summary / Technical Context

Extend the existing Netlify Bonus Campaigns flow with one four-value reward configuration and progression stored in existing receipt metadata. Keep a single generic Claim endpoint, existing ledger and Admin controls. Derive entitlement server-side under locks; separate campaign-local streak from cross-campaign daily payment exclusion.

Backend: existing Node ESM Netlify functions, `postgres`/`beginSql`, Supabase Auth/PostgreSQL. Frontend: existing global/IIFE JS and HTML/CSS; no dependency change. Tests: existing `node:test` behavioral suites, plus one bounded PostgreSQL concurrency test using existing `postgres` in an isolated test database. No unbounded history download, streak table, payout cron, generic reward engine or global promotions lock framework.

## Decisions / data model

1. Reserve `campaign_type='poker_daily'` for the replacement campaigns. The shared Poker Daily family is exactly this type plus legacy code `daily-active-2026`; unrelated generic daily campaigns are not reclassified.
2. Add nullable `bonus_campaigns.daily_rewards` JSONB, API `dailyRewards`, containing exactly four positive safe integers. Old rows default to null and retain fixed amounts. New type requires `claim_policy=daily`, `eligibility_type=all_accounts`, `max_total_claims=null`, and scalar `amount=dailyRewards[0]`. Backend validation and schema constraints reject incomplete/invalid configuration; no silent reward fallback.
3. New campaign receipts carry `metadata.streak_day`, `reward_day=Math.min(streak_day,4)`, `amount`, `daily_bonus_family='poker_daily'`, existing campaign/period keys and `claim_decision_at`. Copy payout provenance into transaction and entry metadata. No extra streak column/table or rewrite of legacy metadata.
4. Yesterday's receipt for the same replacement campaign continues its server-recorded `streak_day`; no receipt yesterday means Day 1. Today's receipt is already claimed, not a new progression. Reads are bounded indexed lookups, not scans of the entire unlimited series. Missing/corrupt new-format metadata or mismatched receipt/ledger evidence denies payout and logs for operator review.
5. Keep `bonus:<campaignCode>:<userId>:<UTC-period>` keys unchanged. Cross-campaign exclusion is an additional transaction check, never a replacement of ledger idempotency.
6. Publish new Poker Daily manually through existing active/Pause/End actions. Reject `scheduled` for the new type and the specific legacy code. Normal Welcome/anniversary/compensation/generic daily scheduling stays available. A future requirement for timed automatic replacement needs its own approval.

## Atomic claim and lifecycle protocol

Extend existing methods in `netlify/functions/_shared/bonus-campaigns.mjs`; small private helpers in that file such as `isPokerDailyCampaign`, `lockPokerDailyBonus`, `readDailyClaimEvidence`, `resolveDailyReward`. Admin imports/reuses the same family predicate/lock rather than duplicating its scope.

**Lock choice**: one transaction-scoped advisory lock in a dedicated `poker_daily_bonus` namespace, only for this family. Existing Claim already serializes through a campaign row lock; a single family lock is the smallest extension that also serializes old/new campaign claims and activation races. No shared lock service/table. It is held for the bounded database transaction, never UI/network waiting. Unrelated promotions do not take it. Potential throughput cost is documented rather than adding multiple lock layers prematurely.

**Claim order**:
1. Authenticate using current `verifySupabaseJwt`; retain campaign preflight as advisory/fast denial. Derive user from verified identity only; never accept amount/day/user/period from POST.
2. Enter `beginSql`. For a scoped Daily, acquire the family lock first; then use `lockCampaign` to select the full current row `FOR UPDATE`, even if it has become inactive. For other campaigns use the same full-row revalidation without family semantics.
3. Inside this transaction fetch current account registration (extend `fetchUserCreatedAt` or its local query to read trusted `auth.users.is_anonymous` for Daily). Require a real non-anonymous account; re-evaluate eligibility with `txSql`. Do not use user-editable metadata or guess a guest from missing email. Hold appropriate registration row lock during the decision. Other campaigns retain their existing audience rules.
4. Obtain DB `clock_timestamp()` after lock waits; derive UTC period using existing `buildClaimPeriodKey`. Use this instant for `starts_at <= instant < ends_at`, reward/status validation and history. Do not reuse preflight `deps.now` or transaction-start `now()` as production authority; deterministic tests inject the transaction clock.
5. Recheck same-campaign receipt/transaction replay, campaign cap for unrelated campaigns, and Daily family evidence for this account/day. Search `bonus_claims` joined to scoped campaigns, plus existing PROMO_BONUS transaction/durable registry evidence where a receipt is absent. For legacy evidence, conservatively block when either its stored UTC period or its actual receipt/payout decision time falls in today's UTC day; this covers historical requests spanning midnight. Never scan arbitrary PROMO_BONUS/Welcome receipts into this family. Ambiguous orphan evidence denies, not grants.
6. Enforce one active family member and legacy retirement: any replacement in `active`, `paused` or `ended` permanently disqualifies further legacy payouts/reactivation. A draft alone does not retire the legacy campaign. Multiple active members/unsafe state -> deny.
7. Read today's/yesterday's new-campaign receipt and compute real streak/reward under the same lock. Revalidate the UTC instant just before posting; if validation straddled the UTC boundary, return `claim_period_changed` without writes, requiring a fresh request. Never auto-mint another period on retry.
8. Pass authoritative amount/provenance to existing `buildBonusCampaignEntries`/`postTransaction(...,tx=sqlTx)`; insert receipt in the same transaction. Set Daily `claimed_at` explicitly to the validated DB decision instant, so transaction-start defaults cannot contradict `claim_period_key`. Include decision instant in ledger metadata; do not change global ledger timestamp conventions.
9. Validate non-null matching transaction/receipt IDs; throw on any inconsistency so everything rolls back. Duplicate returns existing paid amount/day/transaction, not a newly computed next reward. There is no new paid success unless this transaction created the new entitlement receipt.

**Admin order**: `createBonusCampaign`/`updateBonusCampaign`/`setBonusCampaignStatus` use `beginSql` for scoped Daily operations: family lock, full current-row lock, fresh transition/claim-count/config checks, then write. Normalize/report `dailyRewards`; include it in immutable terms. Reject activation if another family member is active; reject legacy reactivation after any published replacement, even while replacement is paused/ended. Refetch after lock, not a stale UI claim count. Wrap published-update checks in the existing transaction path for other campaigns too, preserving their rules. Always acquire family lock before campaign row locks; never attempt it while already holding a campaign row lock.

Existing scheduler needs no additional job or payout logic: schema/Admin deny scoped `scheduled`; normal expiry updates contend with the same campaign row lock. Verify this with regression tests. If current environment contains a scoped scheduled row, preflight blocks migration/rollout; do not silently alter it in a migration.

## Migration plan (one additive migration, not created now)

After approval, use Supabase CLI to allocate the timestamp for `supabase/migrations/<allocated-timestamp>_bonus_campaign_daily_rewards.sql`.

- Add nullable `daily_rewards`; no seeding, campaign status changes or payout/backfill.
- Add scoped reward/type/policy/audience/null-cap constraints, including four positive safe-integer amounts and equality of scalar amount to Day 1. Non-Poker-Daily rows remain valid with null rewards.
- Add scoped manual-activation constraint rejecting `scheduled` for `poker_daily` and legacy code.
- Add `bonus_campaigns_one_poker_daily_active`: unique constant expression for active rows where type is `poker_daily` OR code is `daily-active-2026`. Enforces no overlap even for older Admin SQL/scheduler or unsupported direct writes. Existing conflicts fail migration; never auto-pause/delete to make it pass.
- Add `bonus_claims_user_period_campaign_idx(user_id,claim_period_key,campaign_id)` for bounded cross-campaign period evidence; use existing `(campaign_id,user_id,claim_period_key)` uniqueness for today/yesterday progression and existing user/time index for time evidence.

This planned migration will mutate shared Stage if included in a same-repository migration PR. 2. Implement locally; run fundamental tests against mocks and isolated DB, self-review minimal diff/CSP, identify exact code/migration SHA. No campaign operational changes.
3. **Stage schema GO before migration PR push**: identify exact Stage project/DB and migration SHA, read-only preflight active/scheduled family rows, schema/anonymous-account capability, legacy claim/ledger integrity and GENESIS status. Apply only the additive schema after GO and verify; legacy stays active and untouched.
4. **Stage application Preview GO**: deploy the approved application SHA to Stage/Preview with no new active campaign. Verify schema/read endpoints/Admin/ordinary campaigns. Both the old and new HTTP claim handlers must use the revised atomic path; ensure any old serverless invocations are drained before activation. Schema compatibility alone does not make old code compute streak rewards.
5. **Stage campaign-preparation GO**: through existing Admin create one new draft with reviewed code/dates and `[25,50,100,200]`. No claim yet. Verify no automatic activation path.
6. **Explicit Stage cutover + bounded payout-smoke GO**: pause `daily-active-2026` through existing Admin; wait for admitted in-flight claims to finish and verify pause is authoritative/no ongoing grants. Then activate the verified replacement; confirm exactly one active family member. Audit a historical claimant from today's period is blocked, an unpaid account receives Day 1, retries do not mint and next UTC-day behavior is correct. Real payout smoke requires the stated CH grant permission; do not fabricate historical dates/claims in Stage to simulate future days. Preserve all prior records and audit counts/transaction IDs.
7. After Stage acceptance, **Stage legacy End GO** if desired: end old paused campaign, retaining evidence. Record UTC cutover time, operator, environment, campaign IDs/config, exact application/migration SHA and pre/postflight results using existing logs/history plus a redacted deployment record. Existing Admin `klog` captures updates; no audit subsystem/table added.
8. **Separate Production readiness/schema/application GO**, only after accepted Stage evidence: independently verify Production identity and actual campaigns, do not assume the historical “none active” report still holds. Schema first, then fully updated application, then new draft. No merge without a separate explicit merge instruction.
9. **Separate Production activation/cutover + any payout GO**: if a legacy campaign exists, repeat pause/verify/activate guard sequence; otherwise verify no family member and activate only the reviewed draft. Run a bounded operator-approved smoke and preserve receipt/ledger evidence. No automatic promotion from Stage.

**Rollback**: before activation leave new draft inactive and stop rollout; never remove schema to force old binaries. After activation, Pause the new campaign using existing kill switch; do not reactivate the old 20 CH campaign, refund/rewrite history or downgrade to a binary that treats streak rewards as fixed 25 CH. Keep additive schema, current safe backend and evidence; fix forward and resume only with an environment-specific GO. End is irreversible in current Admin lifecycle.

Single family lock serializes Daily claims; no premature scalability framework.

Environment inventory, orphan/history inconsistencies, actual DB auth capability and cutover timestamp are explicit operator preflight gates.
