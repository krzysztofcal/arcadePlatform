# Data model — projekt, bez migracji

## 1. chips_accounts: trwała klasa USER

Rozszerzyć istniejący wiersz, bez osobnej tabeli fraud: `poker_bot_access` text NOT NULL DEFAULT NORMAL CHECK IN(NORMAL,RESTRICTED); `poker_restricted_at` timestamptz; `poker_restriction_reason` text; `poker_restriction_threshold_ch` bigint; `poker_restriction_balance_ch` bigint. Dla NORMAL metadane null; dla RESTRICTED wymagane reason BALANCE_THRESHOLD,czas,threshold>0,balance>=threshold. Nie-USER zawsze NORMAL/null. Nie używać ogólnego account status: restriction nie zamraża portfela.

Migracja nie klasyfikuje masowo i nie zmienia balance; domyślne NORMAL przechodzi detektor przy pierwszej decyzji. Nieznany/missing USER nie jest NORMAL. Istniejąca unikalność USER/user_id zapewnia jedną trwałą tożsamość. Brak publicznej aktualizacji tych pól; backend-only i istniejące uprawnienia/RLS należy sprawdzić w T002. Nie dawać klientowi UPDATE nowych pól przez istniejący grant na cały wiersz.

Wiersz USER jest wspólną blokadą klasyfikacji i decyzji funding. NORMAL→RESTRICTED tylko raz, nie zmieniać first detected danych. Balance spadający po detekcji nie usuwa stanu. Metadane nie stanowią drugiego ledgera.

## 2. Bez nowej tabeli receipt — istniejący ledger/registry

Nie tworzyć poker_bot_refill_receipts ani innego permanentnego rejestru. Existing chips_transactions/chips_entries i chips_transaction_idempotency zapewniają identity,transaction_id,payload_hash,tx_type,user_id,table_id oraz powiązanie archiwum. Zachować deterministic funding idempotency key seed/replacement/managed top-up. Jeśli D>0, MINT key to deterministyczny prefiks `bot-refill:` + pełny funding key; D=0 oznacza brak MINT i brak dodatkowej tożsamości. MINT i TABLE_BUY_IN oraz ich registry są w jednym tx/savepoint z seat/state.

MINT binding: strict namespace, parser wewnętrznego funding key przez istniejący chips_parse_table_idempotency_key,derived table_id,exact GENESIS→source i paired funding key/transaction id w server-authored metadata. Przechować snapshot kwoty D,source,F i plan version w istniejącym payload/hash; nie przeliczać D do replay. Nie dodawać kolumny per-stack EXPOSURE ani resetowanego counter. MINT namespace/binding rejestrowany i sprawdzany w DB tak samo rygorystycznie jak obecne TABLE binding, nie tylko przez metadata.tableId. Zwykły dowolny MINT nadal poza nową ścieżką.

## 3. Exactly-once i lifecycle retention

Najpierw odczytać original funding registry/hash. Jeśli istnieje zgodny funding, zwrócić istniejący wynik bez mint/funding; jego atomowy commit dowodzi również commit ewentualnego MINT. MINT bez funding przy braku pierwotnej transakcji jest integrity/unknown→zero retry emisji, nie okazja do dokończenia częściowego zapisu. Key/payload mismatch error. Unique race rozwiązać istniejącym savepoint/re-read registry, nie kontynuować aborted SQL. Unknown COMMIT odtwarza registry/state pod tym samym kluczem; brak dowodu sukcesu nie oznacza zgody na nową tożsamość.

Brak registry po cleanup NIE uprawnia do odtworzenia starego funding. Przed każdą nową emisją/funding wymagać istniejącego OPEN table pod lockiem,nieaktywowanego retention/retirement fence,aktualnego locked state version i realnej jeszcze niezaspokojonej seat/stack delty. Deleted/missing/CLOSED/retired/stale plan fail-closed,nigdy implicit recreate table ani nowa wersja starej operacji. Stare seed keys nie stają się nowymi po reuse miejsca; zachować existing key semantics. Cleanup nie kasuje aktywnego OPEN table registry; jeśli unexpectedly missing przy już zrealizowanym stanie, zero mint i recovery. Przegrany race cleanup/funding nie może commitować finansów po aktywacji fence.

Hot retention: strict table-linked MINT idzie istniejącym lifecycle wraz z fundingiem: bot-only7d po spełnieniu istniejących closed/proof/age fences; human odpowiedni existing closed-human30d/hold rules. To nie bezwarunkowy TTL dla aktywnych stołów. Manifest/hash/export→verification→prune hot ledger→registry cleanup→table lifecycle completion według aktualnych procedur. Missing-table retirement dopuszcza nowy MINT namespace tylko przy tym samym kompletnym archive/binding/no-hot proof co powiązany funding. Zachować exclusions/ambiguous/manual review,nie ogólny whitelist wszystkich MINT. Jeśli archiwum dzieli parę przez granicę batch, istniejący durable manifest/registry bindings muszą udowodnić oba elementy przed ukończeniem cleanup; do tego czasu pending w obecnym lifecycle,bez nowego schedulera.

Nowe MINT records nie mogą zostać pominięte przez SQL selectors ani JS shape checks jako permanentne out-of-scope. Wymagane konkretne rozszerzenia w research R7/T016. Aktywne/długowieczne stoły i błędny proof mogą nadal utrzymywać hot data zgodnie z istniejącą polityką; nie obiecywać stałej wielkości całej DB. #1018 nie tworzy odrębnej permanentnej klasy danych ani hot rekordu przy D=0. Archiwalne dowody zachowują dotychczasową politykę archiwum.

## 4. Istniejące dane pozostają

poker_tables/lifecycle_kind/managed_profile_key, poker_state.version, poker_seats.is_bot/status/leave_after_hand i escrow source attribution bez nowych klas/owner/drain. has_human_participant pozostaje one-way: zapis dopiero przy zaakceptowanym human admission/rejoin; commit samej detekcji po odmowie nie ustawia false→true. Seated obejmuje ACTIVE/disconnected i pending leave/roszczenie obecnej ręki; rozbieżność state/seat→unknown dla nowych finansów. Przy wyjściu gate uwalnia człowieka dopiero po zatwierdzonym usunięciu claim/membership. Dodać poker_tables.is_farmer_only boolean NOT NULL DEFAULT false. Marker backend-only, false→true dozwolone, true→false zabronione DB one-way triggerem (rozszerzyć istniejący guard tabeli, nie przebudowywać retention). Nie inferować go z braku ludzi. Zachować przy leave/restart/close; nie reuse/relabel farmer-only do normalnego stołu. Lifecycle STANDARD/CONTINUOUS_BOT pozostaje odrębny: istniejący mixed managed może otrzymać true bez zmiany lifecycle. Nowo utworzony farmer-only ma zwykły lifecycle STANDARD, bez managed_profile/seed. Default false dla legacy; przed nowym admission/funding sprawdzić członkostwo i utrwalić true jeśli już seated human jest RESTRICTED. Kandydat RESTRICTED na normalnym stole nie jest takim seated human: odmowa, bez przejęcia stołu i bez zmiany markera. Brak nowego indeksu bez potrzeby: marker odczytywany po table PK.
