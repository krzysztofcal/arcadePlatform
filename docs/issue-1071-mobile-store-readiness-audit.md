# #1071 — Poker Android/iOS readiness and social-casino audit

Audit date: **2026-10-09**. Code baseline: live `origin/main` revision **33d0ceceb6f77503e9dd6d4630a09a02f92a23c1**. Scope agreement: [#1071](https://github.com/krzysztofcal/arcadePlatform/issues/1071); no additional earlier conversation decisions were available in this session. [SpecKit](../specs/1071-mobile-store-readiness/spec.md).

## Recommendation and present decision

**GO for planning; NO-GO today for both free store publication and monetized publication.** The browser game provides a reusable core, but the repository does not establish mobile packaging, no-ad navigation, compliant deletion, store classification, or physical packaged-app acceptance. These are pending release evidence, not a finding that social poker is prohibited.

Smallest free Android route: improve the existing web experience, then test a **Trusted Web Activity (TWA)** with a narrowly scoped Poker entry point. If optional IAP and iOS are near-term requirements, avoid maintaining two packaging stacks: perform a small **Capacitor-style shell feasibility spike** first and use it for both platforms if authenticated networking and billing work without rewriting browser scripts. That shell recommendation is an engineering inference, not store approval. Keep web Poker playable independently. The owner must choose free-first TWA versus direct shell pilot before implementation.

| Route | Fit and prerequisites | Decision |
| --- | --- | --- |
| Browser/PWA | Retains current origin and scripts. Add install metadata/icons, defined cold-start/offline failure experience and update strategy. No offline poker simulation or cached authenticated API/WS state. Browser install is not store distribution. | First reusable prerequisite; minimal browser path. |
| Android TWA | Browser-rendered HTTPS app; verified website/app association via Digital Asset Links. Requires package/signing/domain ownership and full auth/navigation validation. Android only. | Least work for a free Android pilot after web blockers. [Official overview](https://developer.android.com/develop/ui/views/layout/webapps/trusted-web-activities). |
| Narrow Capacitor-style shell | Reuse web assets with small lifecycle, navigation and store bridges. A local app origin differs from HTTPS; auth redirects, CSP/CORS and WS origin allowlists must be proved. Do not assume remote-page wrapping or a generic plugin satisfies production requirements. | Conditional monetized Android + later iOS path. [Official runtime documentation](https://capacitorjs.com/docs). |
| Native rebuild | Reimplement presentation/auth/network behavior on two platforms; existing WS protocol still authoritative. | No evidence that the added cost is needed; defer until a narrow shell demonstrably fails. |

TWA can integrate Play purchases; it is **not inherently limited to free apps**. Its Digital Goods/Payment Request integration and browser capability availability need a real compatibility spike. Missing billing capability must disable purchases, not silently redirect to web checkout. [Google integration guide](https://developer.chrome.com/docs/android/trusted-web-activity/receive-payments-play-billing).

## Purchase verification and recovery proposal

This is a future interface design, not an implemented billing service. [Release boundary contract](../specs/1071-mobile-store-readiness/contracts/release-boundaries.md) records the proposed invariants.

Use three explicit channels: independent web provider, Play Billing, StoreKit. All map to a stable authenticated account, server-owned SKU catalogue and immutable provider-qualified purchase identity. Browser/shell callbacks request verification and never mint CH or entitlements. Verify provider authenticity, app/package/environment, product, purchase status and ownership; reject pending, unknown and conflicting ownership. Google recommends backend verification before granting purchases. [Play security](https://developer.android.com/google/play/billing/security).

Proposed fulfillment: durable unique purchase record → once-only ledger grant or entitlement change → provider acknowledgment/consumption/finish with retry. Store tokens/transactions are sensitive; do not expose service credentials in a shell. Recovery must survive response loss, duplicate callbacks, reinstall and notification reordering. Query provider state when event order is ambiguous; use periodic reconciliation to recover missed notifications. Apple server APIs/notifications are the intended provider boundary, subject to a separate implementation design. [Server API](https://developer.apple.com/documentation/appstoreserverapi), [Notifications](https://developer.apple.com/documentation/appstoreservernotifications).

CH is consumable: restore must not re-grant spent units. Purchased IAP CH must not expire; any promotional expiry needs separate accounting and clear terms so it cannot expire paid units. Cosmetics are permanent nonconsumable ownership, recoverable on account/reinstall. VIP derives expiry/renewal/grace/revocation from provider state; cancellation alone must not remove the remaining paid period. Refund of already-spent CH needs an owner-approved dispute/compensation policy; do not bypass existing nonnegative ledger invariants or rewrite balances. Keep gameplay WS authoritative and separately verify the ledger/entitlement outcome. Purchase restoration must never attach a purchase to another account based only on a caller-supplied identifier.

## Product-breaking changes to decide

1. Mobile no-ad behavior requires more than wrapping current lobby; shared navigation/account/legal resources may need an explicit mobile boundary.
2. Adult targeting and regional restrictions can reduce reach; no child/family positioning assumed.
3. Selling shared Arcade CH may require separating Poker paid currency or revising the product title. This can change balances/bonus messaging; no migration authorized here.
4. Purchased IAP currency must not expire. Paid versus promotional CH and refund handling may therefore require changes to retention/economy assumptions; approve the compliant accounting policy before designing persistence.
5. Deletion and UGC obligations extend beyond Poker table UI into accounts/public profiles and ledger retention.
6. Packaged auth storage and email return differ from ordinary browser behavior; existing sessions cannot be assumed portable.
7. iOS app quality and ongoing VIP value need product evidence; a generic wrapper or an ad-free subscription benefit does not resolve them.

Audit deliverable is complete when SpecKit coverage, primary-source links and documentation-only diff are reviewed. Free/mobile/monetized readiness stays pending as recorded above.
