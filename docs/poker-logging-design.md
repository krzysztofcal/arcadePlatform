# Poker logging design

Status: design target; no runtime implementation is implied by this document.

Related issue: #765.

## 1. Goals

Poker logging should:

- reduce noise, serialization overhead and log-storage cost;
- preserve complete operational evidence for failures, recovery, accounting, settlement, invariants and deployment identity;
- allow an operator to correlate a problem to a table and hand without logging poker state;
- prevent routine success paths from gradually rebuilding high-volume logging;
- remain compatible with the existing `klog` mechanism and current WS, Netlify and browser architecture.

The normal success path of a hot operation is not automatically an `INFO` event. A player action, bot action, persistence write, broadcast or healthy janitor sweep should be silent unless its outcome provides distinct operational value.

## 2. Severity

### DEBUG

Detailed, temporary diagnostics for a known investigation. Disabled by default.

Use when:

- the event is high-frequency or contains step-level execution detail;
- the same operation already has a stable outcome or failure event;
- the data is useful only while diagnosing one subsystem, table or hand.

Examples: bot decision inputs, autoplay scheduling/start/finish, reconciler batch membership, restore start/apply steps and lobby WS transition traces.

### INFO

A low-frequency, meaningful state transition or operational milestone.

Use when:

- an authoritative lifecycle transition completed;
- the event is useful during normal operations without a paired start/success trace;
- the event is not emitted for every hot-path step.

Examples: `ws_artifact_start`, one terminal accounting close, one guest-table eviction and one compact join or rollover outcome.

Routine persistence success, accepted-action audit success, healthy janitor results and ordinary bot decisions are not `INFO`.

### WARN

A recoverable anomaly, protection decision or degraded path that did not violate correctness.

Use when:

- retry, suppression, recovery, fallback or grace-period logic was activated;
- an unusual technical condition was safely deferred or recovered;
- state remained correct but an operator may need to understand why progress was delayed.

Examples: same-state retry suppression, restore recovery, protected/deferred cleanup, settlement backfill, stale socket invalidation and an unavailable optional notification.

Expected business rejections and normal negative outcomes are not warnings. Invalid buy-in, insufficient balance, occupied seat, closed table and a user declining an action should normally be represented in the protocol/UI without an operational `WARN`.

Repeated identical warnings must be fingerprinted, aggregated or rate-limited.

### ERROR

A failed correctness boundary or unrecovered operation requiring investigation.

Use when:

- persistence, recovery, settlement, ledger, terminal accounting or idempotency fails;
- an invariant is violated;
- the server cannot safely complete the requested lifecycle transition;
- an uncaught exception, unhandled rejection or message-processing failure occurs.

Examples: `poker_terminal_accounting_invariant_failed`, ledger mismatches, settlement/audit/hole-card write failures, corrupted or internally inconsistent persisted state, janitor failure, autoplay deterministic failure and `ws_transport_watchdog_terminate_failed`.

Restore severity depends on impact:

- corrupted or internally inconsistent persisted state that prevents safe continuation is `ERROR`;
- an expected missing/stale restore that is safely handled is `WARN`, `DEBUG` or silent depending on whether an operator can act on it;
- routine successful restore steps are not `INFO`.

Critical `ERROR` events cannot be disabled by runtime filtering.

## 3. Target `klog` contract

The existing contract is `klog(kind, data)`. WS writes structured JSON to stdout/journald, Netlify uses its existing console-backed `klog` sink, and the browser records through `window.KLog`.

The smallest backward-compatible evolution is:

```text
klog(eventName, context, options?)
```

Existing two-argument calls remain technically valid during migration. They are classified as `LEGACY`/`UNSPECIFIED`, not as target `INFO`. `options` may provide:

- `severity`: `DEBUG`, `INFO`, `WARN` or `ERROR`;
- `category`: stable subsystem name.

The normalized envelope may contain:

- timestamp generated by the sink;
- severity;
- stable event name;
- category/subsystem;
- `tableId` when relevant;
- `handId` when relevant;
- `userId` only when required and safe;
- a small structured context payload.

Do not introduce a class hierarchy, new dependency or second logger. Existing injected `klog` callbacks and `klogSafe` remain the integration points. Runtime severity filtering must not be enabled until every retained production poker event has an explicit severity. After migration, CI/guard checks should reject new poker calls without severity.

Journald timestamps remain authoritative for ordering. An envelope timestamp is useful for browser/Netlify consistency but must not replace journal metadata.

## 4. Naming conventions

Event names must be stable lowercase snake case:

```text
poker_<subsystem>_<operation>
poker_<subsystem>_<operation>_failed
ws_<subsystem>_<operation>
ws_<subsystem>_<operation>_failed
```

Rules:

- use one stable prefix (`poker_` for domain/HTTP/browser, `ws_` for WS orchestration);
- include a stable subsystem and operation;
- never interpolate trigger, table ID, error code or other runtime data into the event name;
- put outcome, trigger and reason in fields;
- use a separate `*_failed` event when failure paging, retention or alerting differs from success;
- otherwise prefer one operation event with an `outcome` field instead of start/success/noop variants;
- retain established financial and deployment names when changing them would harm runbooks or automation.

Dynamic `${logPrefix}_...` cleanup names should converge on stable cleanup events with `trigger` and `outcome` fields.

Use a small controlled category dictionary rather than free-form strings:

- `runtime`;
- `transport`;
- `session`;
- `table_lifecycle`;
- `gameplay`;
- `autoplay`;
- `persistence`;
- `recovery`;
- `janitor`;
- `settlement`;
- `accounting`;
- `ledger`;
- `http`;
- `admin`;
- `deployment`.

The list should live in one simple constants module or guard configuration shared by poker logging checks. Adding a category requires review and documentation; it does not require classes, registries or a framework.

## 5. Adding new logs

Every new poker log must state in review:

1. what concrete incident it helps diagnose;
2. why an existing event or durable record is insufficient;
3. expected frequency per action, hand, table, connection or sweep;
4. whether it is in a hot path;
5. which fields are required and safe;
6. severity, category and retention expectation;
7. whether it needs deduplication, aggregation or a TTL-bound debug mode.

Forbidden:

- routine start/success pairs without distinct operational value;
- full state dumps;
- hole cards, deck contents or other private cards;
- tokens, cookies, authorization headers, secrets or connection strings;
- large arrays of table IDs or user IDs;
- full per-user payout/claim maps in general logs;
- arbitrary SQL/runtime messages without normalization and truncation;
- direct `console.log`; application logging uses `klog`.

`userId` is not a default envelope field. It may be included only when a specific incident cannot be correlated safely with tableId, handId, request/operation ID or seat number. Never log display names, nicknames, e-mail addresses or arrays/maps of users. Remove `userId` from aggregate, routine success and list events.

## 6. Runtime log levels

This is a future stage, not part of the initial log-removal PRs.

The target model is deliberately small:

- production and preview have separate default configuration;
- both default to the minimum useful level, normally `INFO`;
- filtering remains disabled while any retained production poker event is `LEGACY`/`UNSPECIFIED`;
- `DEBUG` can be enabled temporarily without restarting WS;
- an override may apply globally, to one category, or to one `tableId`;
- every override has a mandatory TTL and automatically expires;
- changes are made through an existing authenticated admin/operational command path;
- every enable, change and expiration emits an audit event without secrets;
- `ERROR` cannot be disabled;
- overrides are process-local unless a future multi-instance requirement proves that coordination is necessary.

Recommended limits: a short default TTL such as 15 minutes and a bounded maximum such as 60 minutes. Do not add persistent configuration storage solely for debug overrides.

## 7. Minimal admin log viewer

A future viewer may provide:

- recent bounded logs;
- filters for severity, event name, category, table ID, hand ID and time range;
- text search over the safe normalized fields;
- live refresh;
- copying or exporting only the safe normalized event set;
- a control for TTL-bound `DEBUG` on one table.

It must not become a Grafana, Loki or Kibana replacement. It should use a bounded operational endpoint or journald-facing service, not query the poker state/ledger database and not read live runtime state to reconstruct log payloads.

Security requirements:

- reuse the existing admin authorization and deny access by default;
- expose predefined filters only; never accept arbitrary `journalctl` arguments;
- never interpolate request values into shell commands;
- use a fixed command/adapter allowlist if journald access is required;
- enforce hard limits for time range, row count, response bytes and live-refresh duration;
- allowlist response fields and redact identifiers/context before returning data;
- do not expose raw payloads, environment variables or service output outside the normalized poker envelope;
- audit every DEBUG override enable, update, expiry and disable operation;
- rate-limit viewer and override endpoints.

## 8. Retention and storage

Current server logs use stdout captured by journald. Netlify retains function logs through its provider, while browser diagnostics are bounded in local storage for verified admins.

Target policy:

- do not write general or debug logs to Supabase;
- keep `DEBUG` for a short operational window only;
- prefer longer operational retention for `WARN` and `ERROR` than normal `INFO` where infrastructure supports it;
- continue using stdout/journald while it meets operational needs;
- rotate and bound journal storage rather than building application log tables;
- keep browser diagnostics bounded and local;
- ensure a future admin viewer cannot load the poker DB or realtime runtime through broad unbounded queries.

Exact day-based retention should be an infrastructure decision based on disk capacity and incident requirements, not hard-coded into poker runtime.

The current journald setup applies a shared retention policy to the service journal; adding severity to `klog` does not by itself provide different retention periods. Longer `WARN`/`ERROR` retention would require a future infrastructure filter/export or separate storage policy and is not part of the initial design.

## 9. Recommended sequence

1. Reduce existing routine and duplicate logs using measured evidence from #765.
2. Add explicit severity and the normalized backward-compatible `klog` envelope.
3. Apply runtime level filtering.
4. Add TTL-bound dynamic overrides.
5. Add a minimal admin viewer only if operational use justifies it.
6. Add alerts only after event names and severity are stable.

## 10. Non-goals

This design does not introduce:

- a distributed log-management system;
- a full observability dashboard;
- large-scale log storage in Supabase;
- new external logging infrastructure;
- migration from `klog` to another library;
- changes to poker gameplay, persistence, settlement, ledger or cleanup semantics.

Any future browser JavaScript must remain compatible with JSP pages and requires the normal CSP SHA update when a served script changes. Any future CSS must keep one line per selector.
